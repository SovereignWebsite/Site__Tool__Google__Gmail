The API

This tool is the one place where email leaves. Other sites, such as the CRM, prepare emails; this tool checks and sends them, with the person's own Google sign-in, in the person's own browser. There is no server: the "API" is a set of modules other sites import, and a data format in vaults that the person owns.

1. Core modules (import them, pinned to a commit)

Plain JavaScript modules under /app/core/, with no page access, so they run in any browser page and in Node tests.

  • send.js: the sending rules (recipients, no Bcc, no key material in the text, at most 20 a day) and the raw message Gmail takes.
  • signoff.mjs: the sign-off format, shared unedited with the CRM: the draft shape, its hash, the person's signature over it, and the check. Its only import is pki.sgit.ai's keys.js.
  • batch.js: a batch of signed-off drafts: attachment checks, the daily limit, the send order, attachments as MIME parts.
  • compose.js: the send screen's logic.
  • demo/mailbox.js: the synthetic twin of a mailbox, and a stand-in for Gmail that records every send as a simulation.

2. Sending from another site (for example the CRM)

  1. The CRM writes a draft into the person's CRM vault: drafts/<id>.json (one recipient, subject, text, optional reply-to and attachments under drafts/<id>/att/).
  2. The person signs it off in the CRM with their browser key: drafts/<id>.approved.json, a signature over the draft's exact hash and a batch id.
  3. The person opens this tool's Signed batch design. It opens the vault (its key reaches this page once, as a sealed code), checks every sign-off against the person's pinned key, and sends the batch on one confirmation.
  4. For each email it writes sent/<id>.json back into the same vault, so the CRM can log it.

Agents may write drafts. Only a person's sign-off and a person's press send. Signed batches are a proposal until the owner approves the policy line that allows them; today they run in demo only.

3. Messages between us

The first use is email among the team, then the people we already know: an agent prepares the draft, a person presses Send in this tool. No agent reads or sends mail on its own.

4. The same pattern for Calendar (proposed)

A sister tool for Google Calendar would follow the same shape: core modules, a synthetic calendar twin and demo mode first, several designs, the person's own sign-in in their own browser. It needs its own repository and site, and a decision on Google's calendar scopes.

Status

Demo only. Live mode needs the owner to add this site's address to the Google sign-in client. Source code: Site__Tool__Google__Gmail; where each file came from: sources.
